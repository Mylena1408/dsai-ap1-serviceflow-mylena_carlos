 5. COMO PREPARAR A MAQUINA (outro desenvolvedor)
-------------------------------------------------------------------------------

1) Node.js >= 20.9 (o projeto foi testado com 22.23.4).
   Nesta maquina o Node padrao e 18; todos os comandos foram rodados com:
       volta run --node 22 <comando>
   Em outra maquina, basta ter Node 20.9+ no PATH.

2) Clonar e instalar:
       git clone https://github.com/Mylena1408/dsai-ap1-serviceflow-mylena_carlos.git
       cd dsai-ap1-serviceflow-mylena_carlos
       npm ci
       npx prisma generate

   No Windows, clonar em caminho CURTO. Caminhos longos quebram o git, o cloc e
   o PostgreSQL portatil (erro 0xC0000106).

3) Banco PostgreSQL de TESTE (nome deve terminar em _test):
   Opcao A - PostgreSQL ja instalado: criar o banco serviceflow_test.
   Opcao B - PostgreSQL portatil usado aqui (fora do repositorio):
       mkdir ../pgtest && cd ../pgtest
       npm init -y
       npm install embedded-postgres@17.10.0-beta.17
       criar ../pgtest/start.mjs com o conteudo abaixo
       node start.mjs          -> aguardar "READY postgres on 54329"

   ---- start.mjs ----------------------------------------------------------
   import EmbeddedPostgres from "embedded-postgres";
   import { existsSync } from "node:fs";
   const dir = new URL("./data", import.meta.url).pathname.replace(/^\/(\w:)/, "$1");
   const pg = new EmbeddedPostgres({
     databaseDir: dir, user: "serviceflow", password: "<senha-local-de-teste>",
     port: 54329, persistent: true,
     initdbFlags: ["--encoding=UTF8", "--locale-provider=icu", "--icu-locale=en-US", "--locale=C"],
   });
   if (!existsSync(dir)) await pg.initialise();
   await pg.start();
   try { await pg.createDatabase("serviceflow_test"); } catch { /* ja existe */ }
   console.log("READY postgres on 54329");
   const stop = async () => { await pg.stop(); process.exit(0); };
   process.on("SIGINT", stop); process.on("SIGTERM", stop);
   setInterval(() => {}, 1 << 30);
   -------------------------------------------------------------------------
   Os dados ficam em ../pgtest/data e sao reaproveitados ao reiniciar.
   O processo precisa continuar aberto enquanto os testes rodam.

4) Criar .env.test.local na raiz do projeto (NAO versionar; ja esta no
   .gitignore):
       TEST_DATABASE_URL=postgresql://USUARIO:SENHA@127.0.0.1:54329/serviceflow_test?schema=public
   Use credenciais locais de teste. Nunca aponte para o banco de producao.

5) Rodar tudo:
       npm run lint
       npm run typecheck
       npm run test:unit
       npm run test:integration
       DATABASE_URL=postgresql://USUARIO:SENHA@127.0.0.1:54329/serviceflow_dev npm run test:e2e
       npx playwright install chromium     (so na primeira vez)
       AUTH_SECRET=qualquer-valor DATABASE_URL=postgresql://u:p@localhost:5432/x npm run build

   Por que DATABASE_URL no E2E: defeito antigo em playwright.config.ts - sem
   .env, ele grava a palavra "undefined" no DATABASE_URL e recusa rodar. Basta
   informar uma URL de desenvolvimento DIFERENTE do banco de teste.
   (Registrado em NOTES.md; nao corrigido para nao mudar comportamento.)

 6. ARQUITETURA ADOTADA (padrao a seguir nas proximas tarefas)
-------------------------------------------------------------------------------

src/modules/<modulo>/
  domain/          tipos e regras puras. Sem Prisma, Next, React ou I/O.
  application/     ports.ts (interfaces) + casos de uso. Recebem repositorio
                   ou executor de transacao por PARAMETRO. Sem Prisma.
  infrastructure/  implementacao Prisma dos ports.
  index.ts         API publica: monta casos de uso + Prisma. Mantem o
                   parametro "database: PrismaClient = prisma" (os testes de
                   integracao usam).

Infraestrutura comum:
  src/server/db/prisma-errors.ts           tabela UNICA de traducao de erros
                                           (P2002, P2003, P2025, P2034).
  src/server/db/serializable-transaction.ts  transacao Serializable +
                                           traducao + mensagem de fallback.

Regras obrigatorias:
  - Outro modulo so e importado por @/modules/<modulo> (o lint bloqueia o
    resto, inclusive caminhos relativos para outro modulo).

  - Asserções de testes existentes NAO podem mudar. So caminhos de import.
  - Cada caso de uso migrado precisa de teste unitario com repositorio em
    memoria (sucesso + erro). Auxiliar: tests/unit/support/in-memory-transaction.ts
  - Exemplos completos: src/modules/sectors (simples) e src/modules/requests
    (transacoes mais complexas).
